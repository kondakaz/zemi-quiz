# ゼミ GitHub 講座 手順書

はじめて Git や GitHub を使う人向けの手順書です。むずかしい言葉は、たとえ話で先に説明します。コマンド（ターミナルに打つ命令）は、**コピーして貼り、`<ニックネーム>` のように `< >` で書いてある所だけ自分のものに直せば**大丈夫です。

この講座（30分）で、**自分のクイズ問題を1問つくり、みんなのクイズサイトに出します**。今日のゴールは「自分の問題がサイトに出た」まで。全員の問題を解くのは、時間が余ったときでよいです。

- 演習サイト: https://kondakaz.github.io/zemi-quiz/
- リポジトリ（プロジェクトの置き場）: https://github.com/kondakaz/zemi-quiz
- この手順書は、演習サイトの `docs/` にも載ります（だれでも読めます）。個人名や内部の情報は書いていません。

## まず、用語のたとえ表

読み飛ばしてもよいですが、困ったらここに戻ってください。

| 用語 | ひとことで言うと |
| --- | --- |
| Git（ギット） | 変更を記録する道具。**ゲームのセーブ機能**のようなもの |
| GitHub（ギットハブ） | 記録をみんなで置く場所。**Google ドライブのようなもの**（ただし、自動では同期しません。push したときだけ置かれます） |
| リポジトリ | プロジェクトのフォルダ＋変更の記録帳 |
| clone（クローン） | 共有の棚（GitHub）から、自分の PC に**丸ごとコピー**する |
| commit（コミット） | **セーブ**する。いつでもその時点に戻れる。メッセージは「セーブデータの名前」 |
| push（プッシュ） | 自分のセーブを、共有の棚（GitHub）に**置く** |
| pull（プル） | 共有の棚から、最新のセーブを**持ってくる** |
| main（メイン） | **本番**のこと。サイトに出るのは、この main の中身 |
| ブランチ | 本番を汚さないための**下書き用のコピー**（フォルダは増えません。同じフォルダのまま、下書きに切り替わります） |
| Pull Request（PR） | 「この下書きを本番に入れていいですか？」という**お願いの紙** |
| Approve（アプルーブ） | 「見たよ、OK」の**はんこ** |
| マージ | 下書きを、本番に**合流**させる |
| GitHub Pages | GitHub に置いたファイルを、**Web サイトとして見せる**機能 |
| 検査（チェック） | ロボットが自動でする点検。緑＝OK、赤＝直す |
| Codex（コーデックス） | 作業を手伝ってくれる AI アシスタント |
| ターミナル | 文字で命令を打つ画面。開き方: **Mac** は ⌘（コマンド）キー＋スペースを押して「ターミナル」と入力し、Enter。**Windows** はスタートボタンを押して「PowerShell」と入力し、開きます。 |
| cd（シーディー） | フォルダに入る命令。`cd Documents` で、「書類」フォルダに入ります |

全体のイメージは、次のとおりです。

```
 GitHub（共有の棚）          ← みんなのセーブが集まる
   ↑ push（置く）   ↓ clone（丸ごとコピー）／ pull（最新を持ってくる）
 自分の PC（ここで作業して、commit ＝ セーブ）
```

## 第1部 事前準備（宿題・講座の前に済ませる）

当日の30分に収めるため、ここは先に済ませます。できていない人は、当日は隣の人の画面を一緒に見て、先生に知らせてください。

1. **GitHub アカウントを作る**。作ったら、2要素認証（パスワードのほかに、もう1つ確認する仕組み）をオンにします。GitHub の画面で、右上のアイコン → Settings → Password and authentication → Two-factor authentication → Enable two-factor authentication の順に進みます。スマホの認証アプリ（Google Authenticator や GitHub Mobile など）で、画面の QR コードを読み取ります。リカバリーコード（スマホをなくしたときの救済用の番号）は、必ず保存します。
2. **Git と GitHub CLI（gh）を入れる**。Git は「セーブする道具」、gh は「ターミナルから GitHub を使う道具」です。
   - **Mac**: ターミナルで `git --version` と打ちます。ツールの導入画面が出たら、「インストール」を選びます。gh は https://cli.github.com から入れます。
   - **Windows**: https://git-scm.com の「Git for Windows」と、https://cli.github.com の gh を入れます。入れたあと、**PowerShell を開き直します**。

   確認: `git --version` と `gh --version` を打って、どちらもバージョンが出ればOKです。あわせて **Node.js**（検査を手元で動かすための道具）も入れておくと便利です。任意です。入っていなくても、PR の検査で確かめられます。
3. **Codex デスクトップアプリを入れる**。サインインして、起動できる状態にしておきます。
4. **自分の名前とメールアドレスを Git に登録する**。セーブ（commit）に書き込まれ、**公開されます**。先に、メールアドレスを公開しない設定にします。
   1. GitHub の画面で、右上のアイコン → Settings → Emails を開き、**Keep my email addresses private**（メールアドレスを公開しない）を選びます。
   2. 同じ画面に出る **noreply アドレス**（`…@users.noreply.github.com` の形。公開しても困らない代わりの住所）を控えます。
   3. ターミナルで、名前はニックネーム、メールは控えた noreply アドレスにして、次を打ちます。

   ```
   git config --global user.name "ニックネーム"
   git config --global user.email "控えた noreply アドレス"
   ```

   確認: `git config --global user.name` と `git config --global user.email` で、入れた値が出ればOKです。本名や、ふだんのメールアドレスは入れません（理由は、後ろの「公開されるものに注意」）。
5. **GitHub へのログインを済ませる**。ターミナルで `gh auth login` を打ち、質問に答えます。質問は、矢印キーで選んで Enter を押します。選ぶものは、GitHub.com、Git の操作は HTTPS、Git の認証に GitHub のログインを使うかには Yes、ログイン方法は Web ブラウザです。途中で **8文字のコード**が出るので、控えます。ブラウザが開いたら、そのコードを貼って、**Authorize**（許可）を押します。確認: `gh auth status` で、ログイン済みと出ればOKです。
6. **ニックネームを決めて、先生に届ける**。このニックネームを、ファイル名とブランチ名に使います（例: `taro-k`）。使える文字は **半角の英小文字・数字・ハイフンだけ**。**ほかの人と重ならないもの**にします。先生に届けて、重複がないか確かめてもらいます。同じニックネームの人がいると、あとから出した PR が止まってしまいます。届けた名前は、当日は変えません。
7. **先生からの招待を承認する**。先生が、あなたの GitHub のユーザー名あてに、リポジトリ `kondakaz/zemi-quiz` への collaborator（共同作業者）の招待を送ります。登録したメールに届く招待メールのリンクから開いて、**Accept invitation**（招待を受ける）を押します（メールが見つからないときは、GitHub の通知からも開けます）。承認すると、`https://github.com/kondakaz/zemi-quiz` に書き込めるようになります。招待には期限（7日）があるので、早めに承認します。
8. **clone する（自分でコマンドを打つ）**。clone は「共有の棚から、自分の PC に丸ごとコピー」です。まず `cd Documents`（cd ＝ フォルダに入る命令）で「書類」フォルダに入ってから、次を打ちます。

   ```
   cd Documents
   git clone https://github.com/kondakaz/zemi-quiz.git
   cd zemi-quiz
   git status
   ```

   確認: `git status` に `On branch main`（いま本番にいる）と出ます。フォルダの中に `index.html` と `questions/` があります。そのあと、**この `zemi-quiz` フォルダを、Codex アプリで開き直します**。`pwd`（いまいる場所を表示する命令）を打って、出てきた場所を**メモします**（当日、`cd` で迷ったときに使います）。Codex アプリで作業フォルダを選ぶところで、その `zemi-quiz` フォルダを選びます。Windows で、OneDrive が「ドキュメント」を預かっているときは、場所が `OneDrive` の中になることがあります。`pwd` の結果を、そのままメモします。
9. **問題の文を考えてくる**。次の4つを、メモにまとめておきます。当日は、これを写すだけにします。
   - 問題文
   - 選択肢4つ（どれも違う文にする）
   - 正解の番号（**0から数える**。1つ目が正解なら 0、4つ目なら 3）
   - 解説（1〜2文）

   テーマは自由です。Codex に考えてもらってもよいですが、**答えが本当に正しいかは、自分で確かめます**。公開されるので、本名・学籍番号は入れません。
10. **次の「読んでおく」と、第3部の「[Codex に頼むときの約束](#dcodex)」を読む**（3分）。

### 読んでおく: なぜバージョン管理か／Git と GitHub

- **なぜバージョン管理か**: `app_v2_最終_本当に最終.py` のように、ファイル名で版を分けると、どれが最新か、何を変えたか、前に戻せるかが分からなくなります。Git を使うと、ファイルは1つのまま、セーブ（記録）が積み重なります。いつでも前のセーブに戻せて、だれが・いつ・何を変えたかも残ります。
- **Git は道具、GitHub は置き場**: Git は、自分の PC の中で動く、セーブ機能です。GitHub は、そのセーブをみんなで置く、インターネット上の場所（Google ドライブのようなもの）です。
- 「セーブと棚」「ブランチ」「お願いの紙（PR）」は、当日のスライドで見ます。用語は、手順書の最初の表にあります。

### 公開されるものに注意

このリポジトリと演習サイトは **public（だれでも見られる）** です。次のものが公開されます。

- **GitHub のユーザー名**（PR やセーブ（commit）に出る）
- **クイズの作者名として書くニックネーム**
- **セーブ（commit）に記録された名前とメールアドレス**（`user.name` と `user.email`。だから、事前準備4で noreply アドレスにします）

だから、次のようにします。

- **本名・学籍番号は、どこにも書きません**。ニックネームにします。`user.name` も本名にしません。
- すでに本名のユーザー名でアカウントを作っている人は、先生に相談します。

## 第2部 当日の短い流れ

<a id="part2"></a>

`<ニックネーム>` は、先生に届けた自分のニックネームに**置き換えます。`<` と `>` も消して**置き換えます。例: ニックネームが `taro-k` なら、`git switch -c add-quiz-<ニックネーム>` は `git switch -c add-quiz-taro-k` になります。**どのステップも、「Codex に頼む」「自分で打つ」「GitHub の画面」のどれか1つだけ**でやります。「できた印」のコマンドは、どのステップでも、Codex の入力欄ではなく、**ターミナルに自分で打ちます**（見るだけです）。各ステップの「詳しく」は、第3部の同じ番号へのリンクです。

| # | やること | やり方 | 目安 | 詳しく |
| --- | --- | --- | --- | --- |
| 1 | main（本番）を最新にして始める（clone は済んでいる） | 自分で打つ | 2分 | [→1](#d1) |
| 2 | ブランチ（下書き）`add-quiz-<ニックネーム>` を作る | 自分で打つ | 1分 | [→2](#d2) |
| 3 | 問題ファイル `questions/<ニックネーム>.json` を書く | Codex に頼む | 5分 | [→3](#d3) |
| 4 | セーブ（commit）して、棚に送る（push） | Codex に頼む | 3分 | [→4](#d4) |
| 5 | Pull Request（PR・お願いの紙）を作る | GitHub の画面 | 2分 | [→5](#d5) |
| 6 | 名簿の次の人の PR を見て Approve（はんこ）する | GitHub の画面 | 3分 | [→6](#d6) |
| 7 | 自分の PR に Approve が付き、検査が緑なら、**自分で**マージする | GitHub の画面 | 2分 | [→7](#d7) |
| 8 | 1〜2分後に、サイトで自分の問題を見る　**← ゴール** | ブラウザ | 3分 | [→8](#d8) |
| 9 | main に戻って pull する（余った時間か、講座のあと） | 自分で打つ | 1分 | [→9](#d9) |

**守ること**

1. **main（本番）では作業しません。main に直接 push しません。** 必ず自分のブランチ（下書き）で作業します。
2. **Codex への最初の頼み（ステップ3）には、約束の一文を先頭に付けます。** ステップ3の文には、もう入っています。
3. **Codex が git や gh を動かすとき、「実行してよいですか？」と承認を求められることがあります。** コマンドの中身を読んでから承認します。`push --force`・`reset --hard`・`main` への push は、承認せず、止めて先生に聞きます。
4. **自分の PR だけを、自分でマージします。** ほかの人の PR のマージボタンは押しません。

**レビューの順番（輪番）**: 名簿は、先生が前日までに配ります。**自分の PR を出したら、すぐ名簿の次の人の PR を見に行きます**（最後の人は、最初の人の PR）。次の人の PR がまだ出ていなければ、名簿をさらに先へたどって、Approve がまだ付いていない PR を**1つ**見ます。**1つ見れば OK** です。欠席の人は、名簿から飛ばします。自分の PR に **5分たっても Approve が付かなければ、先生に声をかけます**。先生が Approve します。

**困ったら**: [つまずいたとき](#trouble)。検査が赤い、push が拒否された、マージボタンが押せない、のどれも、そこにあります。同じニックネームの人がいるときは、先生に声をかけます。

### ステップ4: セーブして、棚に送る（Codex に頼む）

**いま何をしているか**: 作ったファイルをセーブ（commit）して、共有の棚（GitHub）に送ります（push）。

次の文を、Codex に頼みます。

> `questions/<ニックネーム>.json` だけを add して、「クイズを追加: <ニックネーム>」というメッセージで commit してください。そのあと、ブランチ `add-quiz-<ニックネーム>` を origin に push してください。main には push しないでください。実行する前に、コマンドを見せてください。

（`add` は「セーブに入れるファイルを選ぶ」こと、`origin` は「GitHub 上の自分たちのリポジトリ」の呼び名です。）

承認を求められたら、コマンドを読みます。`git add` の対象が `questions/<ニックネーム>.json` だけで、push の行き先が `add-quiz-<ニックネーム>` なら、承認してOKです。`git add .`・`--force`・`main` への push は、承認しません。

**できた印**: 次を打ちます。`git log -1 --oneline` に自分のセーブの名前（メッセージ）が出ます。`git status` に `nothing to commit`（セーブしていない変更はない）と出ます。

```
git log -1 --oneline
git status
```

→ [詳しく](#d4)

### ステップ5: Pull Request（お願いの紙）を作る（GitHub の画面）

**いま何をしているか**: 「この下書きを本番に入れていいですか？」というお願いの紙（PR）を出します。

1. https://github.com/kondakaz/zemi-quiz を開きます。ファイル一覧の上の黄色いバナーの **Compare & pull request**（比べて PR を作る）を押します。バナーが出ないときは、**Pull requests** タブ → **New pull request** を押し、compare で自分のブランチを選んで、**Create pull request** を押します。
2. base（入れる先）が `main`、compare（入れたい下書き）が `add-quiz-<ニックネーム>` になっていることを確かめます。タイトルは「クイズを追加: <ニックネーム>」にします。
3. 説明の欄の **作者の確認** の4項目を確かめて、`[ ]` を `[x]` にします。**レビュアーへのお願い** の欄は、レビューする人用なので、触りません。
4. **Create pull request**（PR を作る）を押します。

**できた印**: PR のページが開き、タイトルの横に番号（`#12` など）が付きます。しばらくすると、検査が走って、緑のチェックが付きます。赤のときは、[PR に検査の赤が付いた](#trouble-red)を見ます。PR を出した直後に、**Review required**（レビューが必要）や **Merging is blocked**（マージできません）と出るのは、正常です（Approve が付くまでの表示です）。　→ [詳しく](#d5)

<a id="s6"></a>

### ステップ6: 名簿の次の人の PR を見て Approve する（GitHub の画面）

**いま何をしているか**: 相手のお願いの紙を見て、「見たよ、OK」のはんこ（Approve）を押します。

見る PR は、**名簿の次の人の PR** です（最後の人は、最初の人の PR）。まだ出ていなければ、名簿をさらに先へたどって、Approve がまだ付いていない PR を1つ見ます。1つ見れば OK です。自分の PR は、自分では Approve できません。

1. **Pull requests** タブを開き、相手の PR を開きます。タイトルが「クイズを追加: <相手のニックネーム>」の PR です。
2. **Files changed**（変更されたファイル）タブを開き、変更を読みます。見る点: 変更が `questions/<相手のニックネーム>.json` の1ファイルだけ／本名・学籍番号が無い／選択肢が4つで、`answer` の番号（0から数える）が正解を指している／検査が緑。
3. **Review changes**（レビューする）を押します。
4. 一言コメントを書きます。
5. **Approve** を選びます。直してほしい点があるときは **Comment** を選びます。**Request changes は選びません**（誤って選んだら、先生に相談します）。
6. **Submit review**（レビューを送る）を押します。

**できた印**: 相手の PR のページ（Conversation タブ）に、自分の名前で Approve した記録が出ます。　→ [詳しく](#d6)（レビューの見どころ）

<a id="s7"></a>

### ステップ7: 自分の PR をマージする（GitHub の画面）

**いま何をしているか**: はんこが付いたお願いの紙を、自分で本番に合流させます（マージ）。

自分の PR のページで、検査が緑で、Approve が付いていることを確かめます。

1. **Merge pull request**（PR をマージする）を押します。
2. 続けて出る **Confirm merge**（マージを確定する）を押します。

**自分の PR だけを、自分でマージします。** ほかの人の PR のマージボタンは押しません（これは、みんなで守る約束で、GitHub の設定では止められません）。Approve が付かないまま5分たったら、先生に声をかけます。

**できた印**: PR の状態が **Merged**（マージ済み・紫色）になります。　→ [詳しく](#d7)

<a id="s8"></a>

### ステップ8: サイトで自分の問題を見る（今日のゴール）

**いま何をしているか**: 本番に入った問題が、自動でサイトになります（GitHub Pages）。自分の問題が出るか、確かめます。

マージの **1〜2分後**に、ブラウザで次を開きます（`<ニックネーム>` は自分のものです）。

```
https://kondakaz.github.io/zemi-quiz/?id=<ニックネーム>
```

例: `https://kondakaz.github.io/zemi-quiz/?id=taro-k`

自分の問題だけが出ます。出ないときは、次の順に試します。

1. **見つかりませんでした。公開の途中（1〜2分）か、URL のニックネームが違う可能性があります。** と出たら、まず1分待って、再読み込みします。
2. 2分たっても出ないときは、URL のニックネームの綴り（大文字・小文字も）が合っているか確かめます。
3. その画面の **作者から選ぶ** のリンク（`?id=` を付けないトップページ）から開きます。

**できた印**: 自分の問題が出ます（作者のニックネーム付き）。ここまでが、今日のゴールです。時間が余ったら、結果画面の **ほかの問題を選ぶ** や、`?id=` を付けないトップページから、全員の問題を解きます（任意）。　→ [詳しく](#d8)

<a id="s9"></a>

### ステップ9: main に戻って pull する（自分で打つ・余った時間か、講座のあと）

**いま何をしているか**: 自分の PC の本番（main）を、最新にします。ほかの人の問題も手元に来ます。

```
git switch main
git pull
ls questions
```

**できた印**: `ls questions`（フォルダの中身を表示する命令）に、全員のファイルが並びます（自分のも含みます）。　→ [詳しく](#d9)

<a id="dcodex"></a>

### Codex に頼むときの約束

最初の頼み（ステップ3）の先頭に、次の約束の一文を付けます（ステップ3の文に、もう入っています）。

> 作業は、このリポジトリの中だけで行ってください。main ブランチには直接 commit も push もしないでください。force push（`--force`）は使わないでください。git や gh のコマンドは、実行する前に私に見せてください。commit と push は、私が頼んだときだけ行ってください。

- Codex は、頼まれていないことまでやってしまうことがあります。出したコマンドや変更は、実行・承認する前に、**何をするのか読みます**。
- git や gh の操作（commit、push など）では、そのたびに **「実行してよいですか？」と承認を求められることがあります**。承認の前に、コマンドの中身を読みます。
- `force push` は「GitHub 側の記録を、力ずくで上書きする」危ない操作です。使いません。
- 各ステップの「できた印」のコマンドは、**状態を見るだけ**です（何も変えません）。Codex の「できました」は、そのまま信じず、自分で見て確かめます。

### 詳しく ステップ1: main（本番）を最新にして始める

事前準備で clone してから、本番（main）が進んでいることがあります。`git pull` で、最新にしてから始めます。`git status` に `nothing to commit, working tree clean`（変更なし・きれいな状態）と出れば、準備OKです。　→ [第2部 ステップ1](#s1)

<a id="d2"></a>

### 詳しく ステップ2: ブランチ（下書き）を作る

main は、サイトに出る本番です。本番では作業せず、自分用の下書き（ブランチ）を作ります。ブランチ名の先頭は `add-quiz-` にします。　→ [第2部 ステップ2](#s2)

<a id="d3"></a>

### 詳しく ステップ3: 問題ファイルを書く

`questions/_template.json` が、書き方の見本です。これを写して、自分のファイルにします。

**書き方**（`_template.json` の中身そのまま）

```json
{
  "author": "ニックネーム",
  "question": "問題文",
  "choices": ["選択肢1", "選択肢2", "選択肢3", "選択肢4"],
  "answer": 0,
  "explanation": "解説を書きます。"
}
```

- `author` は作者名、`question` は問題文、`choices` は選択肢、`answer` は正解の番号、`explanation` は解説です。
- 見本の `answer` は `0`（1つ目が正解）です。自分の問題では、正解の番号（0〜3）に変えます。
- `choices` は、ちょうど4つ。同じ文を2つ入れません。
- 文字は、必ず半角の `"`（ダブルクォート）で囲みます。最後の項目のあとに `,` を付けません。
- `author`・`question`・`choices`・`explanation` を、**見本の文のまま**にしません（検査で赤になります）。`explanation` の「解説を書きます。」も、必ず書き換えます。

**検査で赤になるもの**（先生が用意した検査が、PR で自動で調べます）

- 変更が `questions/<ニックネーム>.json` の **1ファイルの追加だけ**ではない（ほかのファイルを変えた・消した・2つ以上追加した）。
- ファイル名が、半角英小文字・数字・ハイフン＋小文字の `.json` になっていない（大文字、`_`、空白、`.JSON` など）。
- 見本の値のまま（`author` が「ニックネーム」、`question` が「問題文」、選択肢が「選択肢1〜4」など）。
- `choices` が4つでない、空がある、同じ文が重なっている。
- `answer` が 0〜3 の整数でない。
- JSON（この形式の書き方）の間違い（`,` や `"` の足りない・余り）。

`node scripts/build.mjs --check` は、このうち、問題ファイルの中身とファイル名を調べる検査です（PR の検査と同じものです）。直すところがあると、`エラー: questions/<ニックネーム>.json: 〜してください` と、どのファイルの何が悪いかが日本語で出て、止まります。メッセージの指す所を直して、もう一度動かします。`.DS_Store` などの `.` で始まるファイルは、手元の検査では無視されます（セーブには入れません）。　→ [第2部 ステップ3](#s3)

<a id="d4"></a>

### 詳しく ステップ4: セーブして、棚に送る

commit は、手元でセーブすること。push は、そのセーブを GitHub に送ることです。承認を求められたら、`git add` の対象が自分の問題ファイル1つだけで、push の行き先が自分のブランチなら、承認してOKです。

GitHub の画面でも確かめられます。ブラウザで https://github.com/kondakaz/zemi-quiz を開き、ブランチの一覧から `add-quiz-<ニックネーム>` が選べればOKです。　→ [第2部 ステップ4](#s4)

<a id="d5"></a>

### 詳しく ステップ5: Pull Request（お願いの紙）を作る

PR は、「このブランチを main に入れてください」というお願いの紙です。説明の欄には、先生が用意した **作者の確認** の欄が、最初から入っています。4項目を自分で確かめて、`[ ]` を `[x]` にします（作ったあとに、PR のページで四角を押してチェックを付けてもよいです）。

- ファイル名はニックネームにした
- 本名や学籍番号を書いていない
- 答えと解説は正しい
- Files changed は questions/ の自分の問題ファイル1つの追加だけ

**レビュアーへのお願い** の欄は、レビューする人のための観点の一覧です。作者は触りません（レビューの結果は、レビューのコメントに書きます）。PR を出した直後に **Review required** や **Merging is blocked** と出るのは、正常です。Approve が付いて、検査が緑になると、マージできるようになります。

ターミナルで `gh pr view add-quiz-<ニックネーム>` と打つと、PR の状態が出ます（見るだけです。画面で見るだけでもOKです）。　→ [第2部 ステップ5](#s5)

<a id="d6"></a>

### 詳しく ステップ6: 名簿の次の人の PR を見て Approve する

**だれの PR を見るか**: レビューは、**名簿の次の人の PR を見る輪番**です。最後の人は、最初の人の PR を見ます。名簿は、先生が前日までに配ります。欠席の人は、名簿から飛ばします。

待ちが続かないように、次の流れで動きます。

1. 自分の PR を出したら、**すぐ**名簿の次の人の PR を見に行きます。
2. 次の人の PR がまだ出ていなければ、名簿をさらに先へたどって、Approve がまだ付いていない PR を1つ見ます。**1つ見れば OK** です。
3. 自分の PR に **5分たっても Approve が付かなければ**、先生に声をかけます。先生が Approve します。

自分の PR は、自分では Approve できません。

**今日は、Approve か Comment だけを使います。Request changes は選びません。** Request changes を選ぶと、マージが止まってしまいます。誤って選んだら、先生に相談します。

**レビューの見どころ**

PR の説明には、先生が用意した **レビュアーへのお願い** の3項目があります。これは、見る点の一覧です（四角にチェックを付けなくてOK。結果は、レビューのコメントに書きます）。それに、名前の確認を足したものが、見る点です。

- **ファイル**（お願い1）: Files changed を開き、変更が `questions/<ニックネーム>.json` の1ファイルだけ（追加）であることを確かめます。
- **答えと解説**（お願い2）: `choices` が4つ。`answer` の番号（0から数える）が、本当の正解を指している。自分で問題を解いて確かめます。解説は1〜2文で、答えと合っている。
- **検査**（お願い3）: PR の検査が緑である。赤のときは、赤の理由を作者に伝えます。
- **名前**（作者の確認にもあります）: `author` とファイル名がニックネームで、本名・学籍番号・メールアドレスが、どこにも書かれていない。

確認した項目は、レビューのコメントに書きます（「3項目と名前を確認しました」など）。直してほしい点は、**Comment** で具体的に書きます（「4つ目の選択肢と答えが同じ意味に見えます」など）。直してもらったら、見直して Approve します。ターミナルでは、`gh pr view <番号>` で PR の状態が見られます（見るだけです）。　→ [第2部 ステップ6](#s6)

<a id="d7"></a>

### 詳しく ステップ7: 自分の PR をマージする

マージは、PR の変更を main（本番）に入れることです。**マージするのは、作者本人**です。これは **みんなで守る約束** で、GitHub の設定では止められません（書き込み権のある人なら、ほかの人の PR のマージボタンも押せてしまいます）。**自分の PR だけを、自分でマージします。ほかの人の PR のマージボタンは押しません。**

ブランチを消す案内が出ても、今日は消さなくてOKです。検査の状態は、ターミナルの `gh pr checks` でも見られます（見るだけです）。マージできたら、リポジトリの main の `questions/` フォルダに、自分のファイルが入っています。Approve が付かないまま5分たったら、先生に声をかけます。マージボタンが押せないときは、[マージボタンが押せない](#trouble-merge)を見ます。　→ [第2部 ステップ7](#s7)

<a id="d8"></a>

### 詳しく ステップ8: サイトで自分の問題を見る

マージで main が更新されると、自動でサイトが作り直されます（先生が用意した仕組み）。**1〜2分**かかります。`?id=<ニックネーム>` を付けて開くと、その人の問題だけが出ます。公開がまだ、または URL のニックネームが違うときは、**見つかりませんでした。公開の途中（1〜2分）か、URL のニックネームが違う可能性があります。** と出て、**作者から選ぶ** のリンクが付きます。1〜2分おいて再読み込みします。2分たっても出ないときは、URL のニックネームの綴り（大文字・小文字も）を確かめるか、**作者から選ぶ** から開きます。問題を解き終わると、結果の画面に **ほかの問題を選ぶ** のリンクが出ます。トップページ（`?id=` なし）には、「全問を解く」と、**作者から選ぶ** の一覧（作者名とニックネーム）があります。

**Actions タブ**: リポジトリの **Actions**（自動作業）タブで、**Pages 公開** の作業（実行中は黄色、成功は緑）が見られます。何人か続けてマージすると、途中の作業が **Cancelled**（取り消し）になることがあります。**問題ありません**。最後の作業に、全員分が入ります。　→ [第2部 ステップ8](#s8)

<a id="d9"></a>

### 詳しく ステップ9: main に戻って pull する

GitHub の main（本番）は進みましたが、自分の PC の main はまだ古いままです。pull で、最新を持ってきます。

**補足（任意）: 手元でサイトを見る**

pull した main で、サイトを自分の PC の中で作って、見ることができます（Node.js と Python が要ります）。`index.html` を直接開くと、問題を読み込めません。小さなサーバーを立てて、開きます。

```
node scripts/build.mjs
python3 -m http.server --directory _site 8000
```

Windows では、`python3` の代わりに `py` と打ちます（`py -m http.server --directory _site 8000`）。

ブラウザで `http://localhost:8000/` を開きます。止めるときは、ターミナルで `Ctrl+C` を押します。`_site/` は作業用のフォルダで、セーブ（commit）には入りません。　→ [第2部 ステップ9](#s9)

<a id="trouble"></a>

### つまずいたとき

どの項目も、「何が起きたか → どうすればよいか」の順に書いています。迷ったら、先生に画面を見せてください。

<a id="trouble-push"></a>

#### push が拒否された

- **main（本番）に直接 push しようとした**
  - **何が起きたか**: 出力に `GH006: Protected branch update failed`（保護された main は更新できない）と出ます（先生の設定によっては、`GH013: Repository rule violations found` と出ることもあります。意味は同じです）。main は、PR を通さないと入らないようにしてあります。
  - **どうするか**: 次の手順で、セーブを下書き（ブランチ）に移します。
    1. `git switch -c add-quiz-<ニックネーム>`（いまのセーブが、新しい下書きに付きます）
    2. `git push -u origin add-quiz-<ニックネーム>`
    3. `git branch -f main origin/main`（自分の PC の main を、GitHub の main に合わせ直します。セーブは下書きに残るので、消えません）

    迷ったら、実行する前に先生に見せます。
- **権限がない（`403`、`Permission denied`）**
  - **何が起きたか**: 招待を承認していない、または別のアカウントでログインしています。
  - **どうするか**: `gh auth status` で、ログインしているアカウントを見ます。招待の承認は、事前準備の7です。
- **ブランチ名がすでにある**
  - **どうするか**: 別の名前（`add-quiz-<ニックネーム>-2` など）にします。

<a id="trouble-cd"></a>

#### `fatal: not a git repository` と出た

- **何が起きたか**: `zemi-quiz` フォルダの外で、git のコマンドを打ちました。
- **どうするか**: `cd ~/Documents/zemi-quiz` を打って、フォルダに入ってから、もう一度打ちます（`~` は、自分のホームフォルダのことです）。
- **`cd` で「見つからない」と出たとき**: 事前準備8でメモした場所（`pwd` の結果）に `cd` します。分からなければ、先生に画面を見せます。

<a id="trouble-auth"></a>

#### 認証エラー（ログインできていない）

- `gh auth status` を打って、ログインできているか見ます。
- できていなければ、`gh auth login` をやり直します。Git の操作は **HTTPS** を選びます。
- それでも直らないときは、エラーの全文を Codex に見せて、「原因の候補と、**確認のコマンドだけ**を教えて。設定の書き換えは私が決める」と頼みます。

<a id="trouble-red"></a>

#### PR に検査の赤（×）が付いた

**何が起きたか**: ロボットの検査が、問題を見つけました。

**まず、理由を見ます**: **PR のページの Checks タブ、または検査の欄の Details**（詳細）を開きます。エラーの文が、そこに出ます。Files changed タブの該当ファイルの上に注記が出ることもありますが、出ないこともあります。

そのうえで、エラーの種類で、手元での調べ方が違います。

- **JSON の中身のエラー**（下の表で「手元と PR」と付いた文）は、手元の `node scripts/build.mjs --check` でも同じ文が出ます。手元で直して、確かめられます。
- **「1ファイル追加だけ」のエラー**（下の表の1・2行目）は、手元の `node scripts/build.mjs --check` には出ません。次のコマンドで調べます（見るだけです）。

  ```
  git fetch origin
  git diff --no-renames --name-status origin/main...HEAD
  ```

  `A questions/<ニックネーム>.json` の1行だけで、ファイル名が正しい形（半角英小文字・数字・ハイフン＋小文字の `.json`）なら、OKです。それ以外の行（`M`＝変更、`D`＝削除、`A`＝別のファイルの追加）があるのが原因です。1行だけなのに赤いときは、ファイル名の形が原因です（下の表の2行目）。（`HEAD` は「いま自分がいる下書きの最新の状態」のことです。）

**どうするか**: 出た文ごとに、次の表で直します。

| 出る文（一部） | 何が起きたか | どうするか |
| --- | --- | --- |

#### マージボタンが押せない

- **Approve（はんこ）がまだ**
  - **何が起きたか**: 一番多い原因です。ほかの人の Approve が必要です（自分では付けられません）。
  - **どうするか**: 待ちます。**5分たっても付かなければ**、先生に声をかけます。
- **検査が終わっていない、または赤い**
  - **どうするか**: 緑になるまで待ちます。赤なら、上の「PR に検査の赤（×）が付いた」で直します。
- **PR が競合している（conflicts）と出る**
  - **何が起きたか**: ほかの人と同じファイル名（ニックネーム）を使っている可能性があります。ニックネームが重ならなければ、競合は起きません。
  - **どうするか**: すぐに先生に声をかけます。
- **相手が Comment で、直してほしい点を書いている**
  - **どうするか**: 直して push し、相手に見直しを頼みます。
- ボタンの近くに、足りない条件が書かれています。読んでも分からなければ、先生に見せます。

### 機能追加のブランチ名（issue-）

機能追加のブランチは、小文字の `issue-` で始めます（今日は使いません）。`issue-` で始まるブランチで、`questions/` の中を変更する PR は、検査で赤になります（`issue- ブランチでは questions/ を変更できません` と出ます）。

## 第4部 宿題: 自分のアプリをリポジトリにする

今日の流れは、そのまま自分のアプリに使えます。先に決めておくこと: **秘密は、最初のセーブ（commit）にも入れません**。一度 GitHub に上げた秘密は、あとから消しても、記録帳（履歴）に残ります。その場合は、キーを無効にして作り直します。

### 手順

1. **アプリのフォルダで、`.gitignore` を先に作る**。`.gitignore` は、「記録に入れないものリスト」です。入れるものの例: `.env`、`*.key`、`node_modules/`、`.DS_Store`、ビルドの出力フォルダ。使っている言語の定番の `.gitignore` を、Codex に作ってもらってもOKです。
2. **秘密を点検する**。API キー・パスワード・トークンが、コードの中に書かれていないか見ます。あれば、`.env` に移して、コードは環境変数から読みます。**`.env` や、キーを書いたファイルは、絶対にセーブに入れません**。
3. **リポジトリ（記録帳つきフォルダ）にする**。

   ```
   git init
   git status
   ```

   `git status` の一覧に、`.env` など入れたくないものが**出ていない**ことを確かめてから、次へ進みます。
4. **最初のセーブ（commit）**。

   ```
   git add .
   git status
   git commit -m "最初の commit"
   ```

   `git add .` のあと、もう一度 `git status` を見て、秘密のファイルが入っていないことを確かめます。
5. **GitHub にリポジトリを作って push する**。最初は **private（自分だけが見られる）** にしておきます。

   ```
   gh repo create <アプリ名> --private --source . --remote origin --push
   ```
6. **機能を足すときは、ブランチ → PR → マージを1回やる**。今日と同じ流れで、`git switch -c <機能の名前>` → 編集 → commit → push → PR → マージです。1人で作るときも、PR を使うと、変更の単位が GitHub に残ります。

### Codex に頼むときの文例

> このフォルダを Git のリポジトリにしたいです。まず `.gitignore` を作り、`.env` と、秘密や不要なファイルが入らないようにしてください。そのあと、API キーやパスワードがコードに直接書かれていないかを探して、場所だけ教えてください（書き換えは、私が確認してから）。commit と push は、私が頼むまで行わないでください。
