ゼミ GitHub 講座 手順書

この講座（30分）で、自分のクイズ問題を1問つくり、GitHub で全員のサイトに載せる。やることは、clone → ブランチ → 編集 → commit → push → PR → 相互レビュー → マージ → pull の流れ。この流れが、自分のアプリを GitHub で管理するときにも、そのまま使える。

  • 演習サイト: https://kondakaz.github.io/zemi-quiz/
  • リポジトリ: https://github.com/kondakaz/zemi-quiz
  • 作業は Codex デスクトップアプリ で行う。Codex に頼む文例と、結果を確かめるコマンドを両方書いてある。
  • この手順書は、演習サイトの docs/ にも載る（だれでも読める）。個人名や内部の情報は書いていない。

0. 事前準備（宿題・講座の前に済ませる）

当日の30分に収めるため、ここは先に終わらせておく。できていない人は、当日は隣の人と2人1組になる。

  1. GitHub アカウントを作る。作ったら 2要素認証を有効にする（GitHub の画面で、右上のアイコン → Settings → Password and authentication → Two-factor authentication → Enable two-factor authentication）。リカバリーコードは必ず保存する。
  2. Git を入れる。確認: ターミナルで git --version と打って、バージョンが出ればよい。あわせて Node.js も入れておくと、手元で問題ファイルの検査ができる（任意。入っていなくても、push したあとの PR の検査で確かめられる）。
  3. Codex デスクトップアプリを入れる。サインインして、起動できる状態にしておく。
  4. 自分の名前をGit に登録する（commit に記録される）。 
    git config --global user.name "ニックネーム"
git config --global user.email "メールアドレス"

    確認: git config --global user.name と git config --global user.email で、入れた値が出ればよい。

  5. GitHub への認証を済ませる。ターミナルで gh auth login を実行し、質問に答える。選ぶものは、GitHub.com、Git の操作は HTTPS、Git の認証に GitHub のログインを使うかには Yes、ログイン方法は Web ブラウザ。ブラウザが開いたら、画面の指示に従う。確認: gh auth status で、ログイン済みと出ればよい。（gh が入っていないときは、GitHub CLI を先に入れる。）
  6. ニックネームを決めて、先生に届ける。このニックネームを、ファイル名とブランチ名に使う（例: taro-k）。使える文字は 半角の英小文字・数字・ハイフンだけ。ほかの人と重ならないものにするので、先生に届けて、重複がないか確かめてもらう。同じニックネームの人がいると、あとから出した PR が競合して止まる。届けた名前から、当日は変えない。
  7. 先生からの招待を承認する。先生が GitHub のユーザー名あてに、リポジトリ kondakaz/zemi-quiz への collaborator 招待を送る。登録したメールに届く招待メールのリンクから開いて、承認する（メールが見つからないときは、GitHub の通知からも開ける）。承認すると、https://github.com/kondakaz/zemi-quiz を開いたときに、自分が書き込める側になる。招待には期限（7日）があるので、早めに承認する。

公開されるものに注意

このリポジトリと演習サイトは public（だれでも見られる） である。次のものが公開される。

  • GitHub のユーザー名（PR や commit に出る）
  • クイズの作者名として書くニックネーム
  • commit に記録された名前とメールアドレス（user.name と user.email）

だから、次のようにする。

  • 本名・学籍番号は、どこにも書かない。ニックネームにする。user.name も本名にしない。
  • メールアドレスを公開したくないときは、GitHub の画面で Settings → Emails を開き、Keep my email addresses private を選ぶ。その画面に出る noreply アドレスを、user.email に設定する。
  • すでに本名のユーザー名でアカウントを作っている人は、先生に相談する。

当日の流れ（9ステップ）

#やること目安
1clone: リポジトリを手元に持ってくる3分
2ブランチ add-quiz-<ニックネーム> を作る2分
3問題ファイルを書く7分
4commit して push する3分
5GitHub で Pull Request（PR）を作る2分
6ほかの人の PR を1つ見て Approve する3分

以下、<ニックネーム> は、先生に届けた自分のニックネームに読み替える。ファイル名とブランチ名に使うので、半角の英小文字・数字・ハイフンだけである（例: taro-k）。拡張子 .json も小文字にする。

Codex に頼むときの約束（必ず守る）

Codex は、頼まれていないこともやってしまうことがある。次の文を、最初の依頼に必ず添える。

作業は、このリポジトリの中だけで行ってください。main ブランチには直接 commit も push もしないでください。force push（--force）は使わないでください。ブランチ名は add-quiz-<ニックネーム> にしてください。commit と push は、私が頼んだときだけ行ってください。

  • Codex が出したコマンドや変更は、実行・承認する前に、何をするのか読む。push --force、reset --hard、main への push が出てきたら、承認せず、止めて先生に聞く。
  • 各ステップで、確認用のコマンドを自分で実行して、結果を見る。Codex の「できました」は、そのまま信じない。

ステップ1: clone（手元に持ってくる）

Codex にこう頼む

作業用のフォルダ（わかりやすい場所）に、https://github.com/kondakaz/zemi-quiz.git を clone して、そのフォルダを作業フォルダにしてください。

実際に動くコマンド（確認用）

git clone https://github.com/kondakaz/zemi-quiz.git
cd zemi-quiz
git status

GitHub の画面でやること: なし。

うまくいったかの見分け方: git status に On branch main と出る。フォルダの中に index.html と questions/ がある。

ステップ2: ブランチを作る

main は、サイトに出る本物である。main では作業せず、自分用のブランチ（作業用の枝）を作る。

Codex にこう頼む

add-quiz-<ニックネーム> という名前の新しいブランチを作って、切り替えてください。main には何も変更しないでください。

実際に動くコマンド（確認用）

git switch -c add-quiz-<ニックネーム>
git branch

GitHub の画面でやること: なし（この時点では GitHub にまだ出ない）。

うまくいったかの見分け方: git branch の一覧で、* が add-quiz-<ニックネーム> についている。

ステップ3: 問題ファイルを書く

questions/_template.json が書き方の見本である。これを写して、自分のファイルにする。

Codex にこう頼む

questions/_template.json を questions/<ニックネーム>.json にコピーして、中身を私の問題に書き換えてください。作者名（author）はニックネーム <ニックネーム> にして、本名や学籍番号は入れないでください。問題は「（自分で決めたテーマ）」について、4択で1問、答えと1〜2文の解説をつけてください。ほかのファイルは変更しないでください。

（問題を Codex に考えてもらってもよい。ただし、答えが本当に正しいかは、自分で確かめる。）

書き方

{
  "author": "ニックネーム",
  "question": "問題文",
  "choices": ["選択肢1", "選択肢2", "選択肢3", "選択肢4"],
  "answer": 1,
  "explanation": "解説（1〜2文）"
}
  • choices は、ちょうど4つ。同じ文を2つ入れない。
  • answer は 0から数える 番号（0〜3）。上の例では、"選択肢2" が正解である。
  • 文字は、必ず半角の "（ダブルクォート）で囲む。最後の項目のあとに , を付けない。
  • author・question・choices・explanation を、見本（_template.json）の文のままにしない。

検査で赤になるもの（先生が用意した検査が、PR で自動で調べる）

  • 変更が questions/<ニックネーム>.json の 1ファイルの追加だけではない（ほかのファイルを変えた・消した・2つ以上追加した）。
  • ファイル名が、半角英小文字・数字・ハイフン＋小文字の .json になっていない（大文字、_、空白、.JSON など）。
  • 見本の値のまま（author が「ニックネーム」、question が「問題文」、選択肢が「選択肢1〜4」、など）。
  • choices が4つでない、空がある、同じ文が重なっている。
  • answer が 0〜3 の整数でない。
  • JSON の書き方の間違い（, や " の過不足）。

実際に動くコマンド（確認用）

git status
node scripts/build.mjs --check

（node scripts/build.mjs --check は、PR の検査と同じ、問題ファイルの検査である。Node.js が入っていない端末では動かなくてもよい。その場合は、push したあとの PR の検査で確かめる。）

GitHub の画面でやること: なし。

うまくいったかの見分け方: git status で、変更されたのが questions/<ニックネーム>.json の1ファイルだけ。検査を動かしたときは、2件の問題を確認しました のように出る（先生の見本と自分の分で、少なくとも2件）。直すところがあると、エラー: questions/<ニックネーム>.json: 〜してください と、どのファイルの何が悪いかが日本語で出て、止まる。メッセージの指す所を直して、もう一度動かす。

ステップ4: commit して push する

commit は、手元に変更を「記録」すること。push は、その記録を GitHub に送ること。

Codex にこう頼む

questions/<ニックネーム>.json だけを add して、「クイズを追加: <ニックネーム>」というメッセージで commit してください。そのあと、ブランチ add-quiz-<ニックネーム> を origin に push してください。main には push しないでください。

実際に動くコマンド（確認用）

git add questions/<ニックネーム>.json
git commit -m "クイズを追加: <ニックネーム>"
git push -u origin add-quiz-<ニックネーム>

GitHub の画面でやること: ブラウザで https://github.com/kondakaz/zemi-quiz を開き、ブランチの一覧（ブランチ名の表示されたメニュー）から add-quiz-<ニックネーム> が選べることを見る。

うまくいったかの見分け方: push の出力に add-quiz-<ニックネーム> -> add-quiz-<ニックネーム> と出る。出力に、PR を作るための URL が出ることもある。git log --oneline -1 で、自分のメッセージが一番上に出る。

ステップ5: Pull Request（PR）を作る

PR は、「このブランチを main に入れてください」という依頼である。

Codex にこう頼む

ブランチ add-quiz-<ニックネーム> から main に向けた Pull Request を作ってください。タイトルは「クイズを追加: <ニックネーム>」にしてください。マージはしないでください。

実際に動くコマンド（確認用）

gh pr create --base main --head add-quiz-<ニックネーム> --title "クイズを追加: <ニックネーム>" --body-file .github/pull_request_template.md
gh pr view --web

GitHub の画面でやること（コマンドを使わない場合）: リポジトリのページで、add-quiz-<ニックネーム> のブランチを選ぶ。ファイル一覧の上に Compare & pull request のバナーが出ることがある（出ていれば押す）。base が main、compare が自分のブランチになっていることを確かめ、タイトルと説明を書いて Create Pull Request を押す。説明の欄には、先生が用意した 作者の確認 の欄が最初から入っている。4項目を自分で確かめて、[ ] を [x] にする（作ったあとに、PR のページで四角を押してチェックを付けてもよい）。

  • ファイル名はニックネームにした
  • 本名や学籍番号を書いていない
  • 答えと解説は正しい
  • Files changed は questions/ の自分の問題ファイル1つの追加だけ

（上のコマンドで作るときは、--body-file で、この欄をそのまま説明に入れている。）

うまくいったかの見分け方: PR のページが開き、タイトルの横に番号（#12 など）が付く。しばらくすると、検査（check）が走り、緑のチェックが付く。赤のときは、「つまずいたとき」の「PR に検査の赤が付いた」を見る。

ステップ6: ほかの人の PR を1つ見て Approve する

だれの PR を見るか（規則）: 名簿で 自分の次の人 の PR を見る。名簿の最後の人は、最初の人の PR を見る。その人の PR がまだ出ていなければ、先に出ている別の人の PR を見る（先生か隣の人に聞く）。自分の PR は、名簿で前の人が見てくれる。自分の PR を自分で Approve することはできない。 相手が欠席などで、自分の PR に Approve が付かないときは、先生に声をかける。

Codex にこう頼む（見る前の下調べだけ頼んでよい）

Pull Request #（番号）の変更を読んで、ファイルが1つだけか、本名や学籍番号が書かれていないか、4択で answer の番号が正しいかを、確認してください。コメントや Approve は私が自分で行うので、PR には何も書き込まないでください。

実際に動くコマンド（確認用）

gh pr list
gh pr view <番号>
gh pr diff <番号>
gh pr checks <番号>

GitHub の画面でやること

  1. リポジトリの Pull requests タブを開き、相手の PR を開く。
  2. Files changed タブを開き、変更を読む（下の「レビューの観点」で確かめる）。
  3. Review changes を押す。
  4. 一言コメントを書く（「問題が面白かった」でもよい）。
  5. Approve を選ぶ。直してほしい点があるときは Comment を選ぶ。
  6. Submit review を押す。

うまくいったかの見分け方: 相手の PR のページ（Conversation タブ）に、自分の名前で Approve した記録が出る。

レビューの観点

PR の説明には、先生が用意した レビュアーへのお願い の3項目がある。それに、名前の確認を足したものが、見る点である。

  • ファイル（お願い1）: Files changed を開き、変更が questions/<ニックネーム>.json の1ファイルだけ（追加）であることを確かめる。
  • 答えと解説（お願い2）: choices が4つ。answer の番号（0始まり）が、実際の正解を指している。自分で問題を解いて確かめる。解説は1〜2文で、答えと合っている。
  • 検査（お願い3）: PR の検査が緑である。赤のときは、赤の理由を作者に伝える。
  • 名前（作者の確認にもある）: author と ファイル名がニックネームで、本名・学籍番号・メールアドレスが、どこにも書かれていない。

確認した項目は、レビューのコメントに書く（「3項目と名前を確認しました」など）。

直してほしい点は、Comment で具体的に書く（「4つ目の選択肢と答えが同じ意味に見えます」など）。直してもらったら、見直して Approve する。Request changes は、今日は使わない（選ぶと、その人が取り消すまでマージできなくなる）。

ステップ7: 自分の PR に Approve が付き、検査が緑なら、自分でマージする

マージは、PR の変更を main に入れること。マージするのは、作者本人である。これは みんなで守る約束 で、GitHub の設定では強制されていない（書き込み権のある人なら、ほかの人の PR のマージボタンも押せてしまう）。自分の PR だけを、自分でマージする。ほかの人の PR のマージボタンは押さない。

Codex にこう頼む

自分の PR の状態（検査と Approve）を教えてください。マージはしないでください。

実際に動くコマンド（確認用）

gh pr checks
gh pr status

GitHub の画面でやること: 自分の PR のページを開く。検査が緑で、Approve が付いていれば、Merge pull request のボタンが押せる。押して、続けて出る Confirm merge を押す。ブランチを消す案内が出ても、今日は消さなくてよい。

うまくいったかの見分け方: PR の状態が Merged（紫色）になる。リポジトリの main の questions/ フォルダに、自分のファイルが入っている。

Approve が付かないときは、先生に声をかける（先生が Approve を付けられる）。マージボタンが押せないときは、「つまずいたとき」を見る。

ステップ8: サイトで全員の問題を解く

マージで main が更新されると、自動でサイトが作り直される（先生が用意した仕組み）。1〜2分かかる。

Codex にこう頼む: 頼まなくてよい。ブラウザで見るだけである。

実際に動くコマンド（確認用）: なし。

GitHub の画面でやること: https://kondakaz.github.io/zemi-quiz/ を開く。出ていなければ、1分待って再読み込みする。リポジトリの Actions タブで、Pages 公開 の処理（実行中は黄色、成功は緑）が見られる。何人か続けてマージすると、途中の実行が Cancelled（取り消し）になることがある。問題ではない。最後の実行に、全員分が入る。

うまくいったかの見分け方: クイズに、自分の問題が出る（作者のニックネーム付き）。全員の問題を解いて、正解数を見る。

ステップ9: main に戻って pull する

GitHub の main は変わったが、手元の main はまだ古い。pull で、手元に取り込む。

Codex にこう頼む

main ブランチに切り替えて、origin の main を pull してください。questions/ にあるファイルの一覧を見せてください。

実際に動くコマンド（確認用）

git switch main
git pull
ls questions

GitHub の画面でやること: なし。

うまくいったかの見分け方: ls questions に、全員のファイルが並ぶ（自分のも含む）。

補足（任意）: 手元でサイトを見る

pull した main で、サイトを手元で作って、見ることができる（Node.js と Python が要る）。index.html を直接開くと、問題を読み込めないので、小さなサーバーを立てて開く。

node scripts/build.mjs
python3 -m http.server --directory _site 8000

ブラウザで http://localhost:8000/ を開く。止めるときは、ターミナルで Ctrl+C を押す。_site/ は作業用のフォルダで、commit には入らない。

つまずいたとき

push が拒否された

  • main に直接 push しようとした: 出力に GH006: Protected branch update failed と出る。main は、PR を通さないと入らないようにしてある。次の手順で、ブランチに移す。
    1. git switch -c add-quiz-<ニックネーム>（今の commit が新しいブランチに付く）
    2. git push -u origin add-quiz-<ニックネーム>
    3. git branch -f main origin/main（手元の main を GitHub の main に合わせ直す。ブランチに commit があるので、記録は消えない）

    迷ったら、実行する前に先生に見せる。

  • 権限がない（403、Permission denied）: collaborator の招待を承認していない、または別のアカウントでログインしている。gh auth status で、ログインしているアカウントを見る。招待の承認は、事前準備の7。
  • ブランチ名がすでにある: 別の名前（add-quiz-<ニックネーム>-2 など）にする。

認証エラー

  • gh auth status を実行して、ログインできているか見る。
  • できていなければ、gh auth login をやり直す。Git の操作は HTTPS を選ぶ。
  • それでも直らないときは、エラーの全文を Codex に見せ、「原因の候補と、確認のコマンドだけを教えて。設定の書き換えは私が決める」と頼む。

PR に検査の赤（×）が付いた

赤の理由の見つけ方: エラーは、PR の画面の3か所に出る。

  • Files changed タブの、該当ファイルの上の注記（赤い × の表示）。
  • PR のページの検査の欄の Details、または Checks タブ（検査の実行ログ）。
  • 手元でも、node scripts/build.mjs --check で同じ文が出る。

どのファイルの何が悪いかが、日本語で出る。文言ごとの直し方は、次の表。

出る文（一部）原因直し方

マージボタンが押せない

  • Approve がまだ: 一番多い原因。ほかの人の Approve が必要である（自分では付けられない）。名簿で前の人に頼む。
  • 検査が終わっていない、または赤い: 緑になるまで待つ。赤なら上の手順で直す。
  • PR が競合している（conflicts）と出る: ほかの人と同じファイル名（ニックネーム）を使っている可能性がある。すぐに先生に声をかける。
  • 相手が欠席などで、Approve が来ない: 先生に声をかける。
  • 相手が Comment で直してほしい点を書いている: 直して push し、相手に見直しを頼む。
  • ボタンの近くに、足りない条件が書かれている。読んでも分からなければ、先生に見せる。

宿題: 自分のアプリをリポジトリにする

今日の流れは、そのまま自分のアプリに使える。先に決めておくこと: 秘密は、最初の commit にも入れない。一度 GitHub に上げた秘密は、あとから消しても、履歴に残る（その場合は、キーを無効にして作り直す）。

手順

  1. アプリのフォルダで、.gitignore を先に作る。入れるものの例: .env、*.key、node_modules/、.DS_Store、ビルドの出力フォルダ。使っている言語の定番の .gitignore を、Codex に作ってもらってもよい。
  2. 秘密を点検する。API キー・パスワード・トークンが、コードの中に書かれていないか。あれば、.env に移して、コードは環境変数から読む。.env や、キーを書いたファイルは、絶対に commit しない。
  3. リポジトリにする。 
    git init
git status

    git status の一覧に、.env など入れたくないものが出ていないことを確かめてから、次へ進む。

  4. 最初の commit。 
    git add .
git status
git commit -m "最初の commit"

    git add . のあと、もう一度 git status を見て、秘密のファイルが入っていないことを確かめる。

  5. GitHub にリポジトリを作って push する。最初は private（自分だけが見られる） にしておく。 
    gh repo create <アプリ名> --private --source . --remote origin --push
  6. 機能を足すときは、ブランチ → PR → マージを1回やる。今日と同じ流れで、git switch -c <機能の名前> → 編集 → commit → push → PR → マージ。1人で作るときも、PR を使うと、変更の単位が GitHub に残る。

Codex に頼むときの文例

このフォルダを Git のリポジトリにしたいです。まず .gitignore を作り、.env と、秘密や不要なファイルが入らないようにしてください。そのあと、API キーやパスワードがコードに直接書かれていないかを探して、場所だけ教えてください（書き換えは、私が確認してから）。commit と push は、私が頼むまで行わないでください。
