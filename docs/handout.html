ゼミ GitHub 講座 手順書

この講座（30分）で、自分のクイズ問題を1問つくり、GitHub で全員のサイトに載せる。今日の到達点は 「自分の問題がサイトに出た」 まで。全員の問題を解くのは、時間が余ったときでよい。

  • 演習サイト: https://kondakaz.github.io/zemi-quiz/
  • リポジトリ: https://github.com/kondakaz/zemi-quiz
  • この手順書は、演習サイトの docs/ にも載る（だれでも読める）。個人名や内部の情報は書いていない。

第1部 事前準備（宿題・講座の前に済ませる）

当日の30分に収めるため、ここは先に終わらせておく。できていない人は、当日は隣の人の画面を一緒に見て、先生に知らせる（レビューの組は、2人1組のまま変わらない）。

  1. GitHub アカウントを作る。作ったら 2要素認証を有効にする（GitHub の画面で、右上のアイコン → Settings → Password and authentication → Two-factor authentication → Enable two-factor authentication）。リカバリーコードは必ず保存する。
  2. Git を入れる。確認: ターミナルで git --version と打って、バージョンが出ればよい。あわせて Node.js も入れておくと、手元で問題ファイルの検査ができる（任意。入っていなくても、PR の検査で確かめられる）。
  3. Codex デスクトップアプリを入れる。サインインして、起動できる状態にしておく。
  4. 自分の名前とメールアドレスを Git に登録する（commit に記録され、公開される）。先に、メールアドレスを公開しない設定にする。
    1. GitHub の画面で、右上のアイコン → Settings → Emails を開き、Keep my email addresses private を選ぶ。
    2. 同じ画面に出る noreply アドレス（…@users.noreply.github.com の形）を控える。
    3. ターミナルで、名前はニックネーム、メールは控えた noreply アドレスにして、次を打つ。
    git config --global user.name "ニックネーム"
git config --global user.email "控えた noreply アドレス"

    確認: git config --global user.name と git config --global user.email で、入れた値が出ればよい。本名や、普段のメールアドレスは入れない（理由は、後ろの「公開されるものに注意」）。

  5. GitHub への認証を済ませる。ターミナルで gh auth login を実行し、質問に答える。選ぶものは、GitHub.com、Git の操作は HTTPS、Git の認証に GitHub のログインを使うかには Yes、ログイン方法は Web ブラウザ。ブラウザが開いたら、画面の指示に従う。確認: gh auth status で、ログイン済みと出ればよい。（gh が入っていないときは、GitHub CLI を先に入れる。）
  6. ニックネームを決めて、先生に届ける。このニックネームを、ファイル名とブランチ名に使う（例: taro-k）。使える文字は 半角の英小文字・数字・ハイフンだけ。ほかの人と重ならないものにするので、先生に届けて、重複がないか確かめてもらう。同じニックネームの人がいると、あとから出した PR が競合して止まる。届けた名前から、当日は変えない。
  7. 先生からの招待を承認する。先生が GitHub のユーザー名あてに、リポジトリ kondakaz/zemi-quiz への collaborator 招待を送る。登録したメールに届く招待メールのリンクから開いて、承認する（メールが見つからないときは、GitHub の通知からも開ける）。承認すると、https://github.com/kondakaz/zemi-quiz を開いたときに、自分が書き込める側になる。招待には期限（7日）があるので、早めに承認する。
  8. clone する（自分でコマンドを打つ）。ターミナルで、作業用のフォルダに移ってから実行する。 
    git clone https://github.com/kondakaz/zemi-quiz.git
cd zemi-quiz
git status

    確認: git status に On branch main と出る。フォルダの中に index.html と questions/ がある。そのあと、この zemi-quiz フォルダを、Codex アプリで開き直す（Codex の作業フォルダが、このフォルダになっている状態にする）。

  9. 問題の文を考えてくる。次の4つを、メモにまとめておく。当日は、これを写すだけにする。
    • 問題文
    • 選択肢4つ（どれも違う文にする）
    • 正解の番号（0から数える。1つ目が正解なら 0、4つ目なら 3）
    • 解説（1〜2文）

    テーマは自由。Codex に考えてもらってもよいが、答えが本当に正しいかは、自分で確かめる。公開されるので、本名・学籍番号は入れない。

  10. 次の「読んでおく」を読む（3分）。

読んでおく: なぜバージョン管理か／Git と GitHub

  • なぜバージョン管理か: app_v2_最終_本当に最終.py のように、ファイル名で版を管理すると、どれが最新か、何を変えたか、前の状態に戻せるかが分からなくなる。Git を使うと、ファイルは1つのまま、変更が「記録」として積まれる。いつでも前の状態を見られて、だれが・いつ・何を変えたかも残る。
  • Git は道具、GitHub は置き場: Git は、自分のパソコンの中で動いて、変更の記録を取る道具である。GitHub は、その記録を置いて、みんなで共有する、インターネット上の場所である。記録をまとめて入れる場所を「リポジトリ」と呼ぶ。
  • 手元と GitHub の関係（clone・commit・push・pull）、ブランチ、PR は、当日のスライドで見る。用語は、手順書の最後の表にある。

公開されるものに注意

このリポジトリと演習サイトは public（だれでも見られる） である。次のものが公開される。

  • GitHub のユーザー名（PR や commit に出る）
  • クイズの作者名として書くニックネーム
  • commit に記録された名前とメールアドレス（user.name と user.email。だから、事前準備4で noreply アドレスにする）

だから、次のようにする。

  • 本名・学籍番号は、どこにも書かない。ニックネームにする。user.name も本名にしない。
  • すでに本名のユーザー名でアカウントを作っている人は、先生に相談する。

第2部 当日の短い流れ

<ニックネーム> は、先生に届けた自分のニックネームに読み替える。どのステップも、「Codex に頼む」「自分で打つ」「GitHub の画面」のどれか1つだけでやる。同じことを両方でやらない。各ステップの「詳しく」は、第3部の同じ番号へのリンク。

守ること

  1. main では作業しない。main に直接 push しない。 必ず自分のブランチで。
  2. Codex への最初の依頼（ステップ3）には、約束の一文を先頭に付ける。 ステップ3の依頼文には、もう入っている。
  3. Codex が git や gh を動かすときは、承認を求められることがある。 コマンドの中身を読んでから承認する。push --force・reset --hard・main への push は承認せず、止めて先生に聞く。
  4. 自分の PR だけを、自分でマージする。 ほかの人の PR のマージボタンは押さない。

困ったら: つまずいたとき。検査が赤い、push が拒否された、マージボタンが押せない、のどれも、そこにある。Approve が付かないとき、同じニックネームの人がいるときは、先生に声をかける。

ステップ1: main を最新にして始める（自分で打つ）

clone した zemi-quiz フォルダで、次を打つ。

git switch main
git pull

できた印: git branch --show-current を打つと main と出る。　→ 詳しく

ステップ2: ブランチを作る（自分で打つ）

git switch -c add-quiz-<ニックネーム>

できた印: git branch --show-current を打つと add-quiz-<ニックネーム> と出る。　→ 詳しく

ステップ3: 問題ファイルを書く（Codex に頼む）

次の文を、Codex にそのまま頼む（<ニックネーム> と、問題の4項目は自分のものに直す）。先頭の約束の一文は、消さない。

約束: 作業は、このリポジトリの中だけで行ってください。main ブランチには直接 commit も push もしないでください。force push（--force）は使わないでください。git や gh のコマンドは、実行する前に私に見せてください。commit と push は、私が頼んだときだけ行ってください。

依頼: questions/_template.json を questions/<ニックネーム>.json にコピーして、中身を、次の問題に書き換えてください。作者名（author）は <ニックネーム> にしてください。ほかのファイルは変更しないでください。

問題文: （考えてきた問題文）
選択肢: （4つ）
正解の番号（0から数える）: （番号）
解説: （1〜2文）

できた印: 次を打つ。git status の Untracked files の下に、questions/<ニックネーム>.json が1つだけ出る。検査は 2件の問題を確認しました のように出る（Node.js が無ければ、検査は飛ばしてよい）。

git status
node scripts/build.mjs --check

→ 詳しく（書き方の見本・検査で赤になるもの）

ステップ4: commit して push する（Codex に頼む）

次の文を、Codex に頼む。

questions/<ニックネーム>.json だけを add して、「クイズを追加: <ニックネーム>」というメッセージで commit してください。そのあと、ブランチ add-quiz-<ニックネーム> を origin に push してください。main には push しないでください。実行する前に、コマンドを見せてください。

承認を求められたら、コマンドを読む。git add の対象が questions/<ニックネーム>.json だけで、push の行き先が add-quiz-<ニックネーム> なら、承認してよい。git add .・--force・main への push は、承認しない。

できた印: 次を打つ。1行目に自分の commit のメッセージが出て、2行目に nothing to commit と出る。

git log -1 --oneline
git status

→ 詳しく

ステップ5: Pull Request（PR）を作る（GitHub の画面）

  1. https://github.com/kondakaz/zemi-quiz を開く。ファイル一覧の上の黄色いバナーの Compare & pull request を押す（出ないときは、ブランチを選んで、Pull requests タブから新しい PR を作る）。
  2. base が main、compare が add-quiz-<ニックネーム> になっていることを確かめる。タイトルは「クイズを追加: <ニックネーム>」にする。
  3. 説明の欄の 作者の確認 の4項目を確かめて、[ ] を [x] にする。
  4. Create pull request を押す。

できた印: PR のページが開き、タイトルの横に番号（#12 など）が付く。しばらくすると、検査が走り、緑のチェックが付く。赤のときは、PR に検査の赤が付いた。　→ 詳しく

ステップ6: 組の相手の PR を見て Approve する（GitHub の画面）

組は、先生が前日までに決めて知らせる（2人1組。奇数なら、1組だけ3人）。自分の PR は、自分では Approve できない。

  1. Pull requests タブを開き、相手の PR を開く。
  2. Files changed タブを開き、変更を読む。見る点: 変更が questions/<相手のニックネーム>.json の1ファイルだけ／本名・学籍番号が無い／選択肢が4つで、answer の番号（0始まり）が正解を指している／検査が緑。
  3. Review changes を押す。
  4. 一言コメントを書く。
  5. Approve を選ぶ。直してほしい点があるときは Comment を選ぶ。Request changes は選ばない（誤って選んだら、先生に相談する）。
  6. Submit review を押す。

できた印: 相手の PR のページ（Conversation タブ）に、自分の名前で Approve した記録が出る。相手がまだ PR を出していないときは、少し待つか、先生に声をかける。　→ 詳しく（レビューの観点）

ステップ7: 自分の PR をマージする（GitHub の画面）

自分の PR のページで、検査が緑で、Approve が付いていることを確かめる。

  1. Merge pull request を押す。
  2. 続けて出る Confirm merge を押す。

自分の PR だけを、自分でマージする。 ほかの人の PR のマージボタンは押さない（これは、みんなで守る約束で、GitHub の設定では強制されていない）。Approve が付かないときは、先生に声をかける。

できた印: PR の状態が Merged（紫色）になる。　→ 詳しく

ステップ8: サイトで自分の問題を見る（今日の到達点）

マージの 1〜2分後に、ブラウザで次を開く（<ニックネーム> は自分のもの）。

https://kondakaz.github.io/zemi-quiz/?id=<ニックネーム>

自分の問題だけが出る。まだ公開されていません と出たら、公開の途中なので、1分待って再読み込みする。リポジトリの Actions タブで、Pages 公開 の処理（実行中は黄色、成功は緑）が見られる。続けてマージすると、途中の実行が Cancelled になることがあるが、問題ではない（最後の実行に、全員分が入る）。

できた印: 自分の問題が出る（作者のニックネーム付き）。ここまでが、今日の到達点。時間が余ったら、?id= を付けないトップページで、全員の問題を解く（任意）。　→ 詳しく

git switch main

ls questions

第3部 詳しい説明とつまずいたとき（参照）

各ステップの補足と、困ったときの直し方。当日の手順（コマンド・依頼文・ボタンの順）は、第2部にある。

Codex に頼むときの約束

最初の依頼（ステップ3）の先頭に、次の約束の一文を付ける（ステップ3の依頼文に、もう入っている）。

作業は、このリポジトリの中だけで行ってください。main ブランチには直接 commit も push もしないでください。force push（--force）は使わないでください。git や gh のコマンドは、実行する前に私に見せてください。commit と push は、私が頼んだときだけ行ってください。

  • Codex は、頼まれていないこともやってしまうことがある。出したコマンドや変更は、実行・承認する前に、何をするのか読む。
  • git や gh の操作（commit、push など）では、そのたびに 承認を求められることがある。承認の前に、コマンドの中身を読む。
  • 各ステップの「できた印」のコマンドは、読み取りだけ（状態を見るだけ）である。Codex の「できました」は、そのまま信じず、自分で見て確かめる。

詳しく ステップ1: main を最新にして始める

事前準備で clone したときから、main が進んでいることがある。git pull で、最新にしてから始める。git status に nothing to commit, working tree clean（変更なし）と出れば、きれいな状態である。　→ 第2部 ステップ1

詳しく ステップ2: ブランチを作る

main は、サイトに出る本物である。main では作業せず、自分用のブランチ（作業用の枝）を作る。ブランチ名の先頭は add-quiz- にする。機能追加のブランチは、小文字の issue- で始める（今日は使わない）。issue- で始まるブランチで、questions/ の中を変更する PR は、検査で赤になる。　→ 第2部 ステップ2

詳しく ステップ3: 問題ファイルを書く

questions/_template.json が書き方の見本である。これを写して、自分のファイルにする。

書き方（_template.json の中身そのまま）

{
  "author": "ニックネーム",
  "question": "問題文",
  "choices": ["選択肢1", "選択肢2", "選択肢3", "選択肢4"],
  "answer": 0,
  "explanation": "解説を書きます。"
}
  • 見本の answer は 0（1つ目の選択肢が正解）。自分の問題では、正解の番号（0〜3）に変える。
  • choices は、ちょうど4つ。同じ文を2つ入れない。
  • 文字は、必ず半角の "（ダブルクォート）で囲む。最後の項目のあとに , を付けない。
  • author・question・choices・explanation を、見本の文のままにしない（検査で赤になる）。explanation の「解説を書きます。」も、必ず書き換える。

検査で赤になるもの（先生が用意した検査が、PR で自動で調べる）

  • 変更が questions/<ニックネーム>.json の 1ファイルの追加だけではない（ほかのファイルを変えた・消した・2つ以上追加した）。
  • ファイル名が、半角英小文字・数字・ハイフン＋小文字の .json になっていない（大文字、_、空白、.JSON など）。
  • 見本の値のまま（author が「ニックネーム」、question が「問題文」、選択肢が「選択肢1〜4」、など）。
  • choices が4つでない、空がある、同じ文が重なっている。
  • answer が 0〜3 の整数でない。
  • JSON の書き方の間違い（, や " の過不足）。

node scripts/build.mjs --check は、このうち、問題ファイルの中身とファイル名を調べる検査である（PR の検査と同じもの）。直すところがあると、エラー: questions/<ニックネーム>.json: 〜してください と、どのファイルの何が悪いかが日本語で出て、止まる。メッセージの指す所を直して、もう一度動かす。.DS_Store などの . で始まるファイルは、手元の検査では無視される（commit には入れない）。　→ 第2部 ステップ3

詳しく ステップ4: commit して push する

commit は、手元に変更を「記録」すること。push は、その記録を GitHub に送ること。承認を求められたら、git add の対象が自分の問題ファイル1つだけで、push の行き先が自分のブランチなら、承認してよい。

GitHub の画面でも確かめられる。ブラウザで https://github.com/kondakaz/zemi-quiz を開き、ブランチの一覧から add-quiz-<ニックネーム> が選べればよい。　→ 第2部 ステップ4

詳しく ステップ5: Pull Request（PR）を作る

PR は、「このブランチを main に入れてください」という依頼である。説明の欄には、先生が用意した 作者の確認 の欄が、最初から入っている。4項目を自分で確かめて、[ ] を [x] にする（作ったあとに、PR のページで四角を押してチェックを付けてもよい）。

  • ファイル名はニックネームにした
  • 本名や学籍番号を書いていない
  • 答えと解説は正しい
  • Files changed は questions/ の自分の問題ファイル1つの追加だけ

ターミナルで gh pr view add-quiz-<ニックネーム> と打つと、PR の状態が出る（読み取りだけ。画面で見るだけでもよい）。　→ 第2部 ステップ5

詳しく ステップ6: 組の相手の PR を見て Approve する

だれの PR を見るか: レビューは、2人1組で互いに見合う。組は、先生が前日までに決めて、知らせる（人数が奇数のときは、1組だけ3人で、順に次の人の PR を見る）。自分の PR は、組の相手が見てくれる。自分の PR を自分で Approve することはできない。 組の相手がまだ PR を出していないときは、少し待つか、先生に声をかける。欠席や遅れで、自分の PR に Approve が付かないときも、先生に声をかける（先生が Approve を付けられる）。

今日は、Approve か Comment だけを使う。Request changes は選ばない。 誤って Request changes を選んだら、先生に相談する。

レビューの観点

PR の説明には、先生が用意した レビュアーへのお願い の3項目がある。それに、名前の確認を足したものが、見る点である。

  • ファイル（お願い1）: Files changed を開き、変更が questions/<ニックネーム>.json の1ファイルだけ（追加）であることを確かめる。
  • 答えと解説（お願い2）: choices が4つ。answer の番号（0始まり）が、実際の正解を指している。自分で問題を解いて確かめる。解説は1〜2文で、答えと合っている。
  • 検査（お願い3）: PR の検査が緑である。赤のときは、赤の理由を作者に伝える。
  • 名前（作者の確認にもある）: author と ファイル名がニックネームで、本名・学籍番号・メールアドレスが、どこにも書かれていない。

確認した項目は、レビューのコメントに書く（「3項目と名前を確認しました」など）。直してほしい点は、Comment で具体的に書く（「4つ目の選択肢と答えが同じ意味に見えます」など）。直してもらったら、見直して Approve する。ターミナルでは、gh pr view <番号> で PR の状態が見られる（読み取りだけ）。　→ 第2部 ステップ6

詳しく ステップ7: 自分の PR をマージする

マージは、PR の変更を main に入れること。マージするのは、作者本人である。これは みんなで守る約束 で、GitHub の設定では強制されていない（書き込み権のある人なら、ほかの人の PR のマージボタンも押せてしまう）。自分の PR だけを、自分でマージする。ほかの人の PR のマージボタンは押さない。

ブランチを消す案内が出ても、今日は消さなくてよい。検査の状態は、ターミナルの gh pr checks でも見られる（読み取りだけ）。マージできたら、リポジトリの main の questions/ フォルダに、自分のファイルが入っている。Approve が付かないときは、先生に声をかける。マージボタンが押せないときは、マージボタンが押せないを見る。　→ 第2部 ステップ7

詳しく ステップ8: サイトで自分の問題を見る

マージで main が更新されると、自動でサイトが作り直される（先生が用意した仕組み）。1〜2分かかる。?id=<ニックネーム> を付けて開くと、その人の問題だけが出る。公開がまだなら、まだ公開されていません と出る。トップページ（?id= なし）には、作者の一覧から選べる入口もある。

Actions タブ: リポジトリの Actions タブで、Pages 公開 の処理（実行中は黄色、成功は緑）が見られる。何人か続けてマージすると、途中の実行が Cancelled（取り消し）になることがある。問題ではない。最後の実行に、全員分が入る。　→ 第2部 ステップ8

詳しく ステップ9: main に戻って pull する

GitHub の main は変わったが、手元の main はまだ古い。pull で、手元に取り込む。

補足（任意）: 手元でサイトを見る

pull した main で、サイトを手元で作って、見ることができる（Node.js と Python が要る）。index.html を直接開くと、問題を読み込めないので、小さなサーバーを立てて開く。

node scripts/build.mjs
python3 -m http.server --directory _site 8000

ブラウザで http://localhost:8000/ を開く。止めるときは、ターミナルで Ctrl+C を押す。_site/ は作業用のフォルダで、commit には入らない。　→ 第2部 ステップ9

つまずいたとき

push が拒否された

  • main に直接 push しようとした: 出力に GH006: Protected branch update failed と出る（先生の設定の種類によっては、GH013: Repository rule violations found と出ることもある。意味は同じ）。main は、PR を通さないと入らないようにしてある。次の手順で、ブランチに移す。
    1. git switch -c add-quiz-<ニックネーム>（今の commit が新しいブランチに付く）
    2. git push -u origin add-quiz-<ニックネーム>
    3. git branch -f main origin/main（手元の main を GitHub の main に合わせ直す。ブランチに commit があるので、記録は消えない）

    迷ったら、実行する前に先生に見せる。

  • 権限がない（403、Permission denied）: collaborator の招待を承認していない、または別のアカウントでログインしている。gh auth status で、ログインしているアカウントを見る。招待の承認は、事前準備の7。
  • ブランチ名がすでにある: 別の名前（add-quiz-<ニックネーム>-2 など）にする。

認証エラー

  • gh auth status を実行して、ログインできているか見る。
  • できていなければ、gh auth login をやり直す。Git の操作は HTTPS を選ぶ。
  • それでも直らないときは、エラーの全文を Codex に見せ、「原因の候補と、確認のコマンドだけを教えて。設定の書き換えは私が決める」と頼む。

PR に検査の赤（×）が付いた

赤の理由の見つけ方: まず、PR のページの Checks タブ、または検査の欄の Details を開く。エラーの文が、そこに出る。Files changed タブの該当ファイルの上に注記が出ることもあるが、出ないこともある。

そのうえで、エラーの種類で、手元での調べ方が違う。

  • JSON の中身・ファイル名のエラー（下の表の2行目以降）は、手元の node scripts/build.mjs --check でも同じ文が出る。手元で直して、確かめられる。
  • 「1ファイル追加だけ」のエラー（下の表の1行目）は、手元の node scripts/build.mjs --check には出ない。次のコマンド（読み取りだけ）で調べる。 
    git fetch origin
git diff --name-status origin/main...HEAD

    A questions/<ニックネーム>.json の1行だけなら正しい。それ以外の行（M＝変更、D＝削除、A＝別のファイルの追加）があるのが原因である。

どの文が出たかで、直し方が違う。

出る文（一部）原因直し方
Checks の注記: 変更一覧を確認し、問題ファイル1つの追加だけにしてください ／ Details のログ: エラー: questions/<ニックネーム>.json を1つ追加するだけにしてください と、その下の変更一覧（A・M・D）PR の変更が、問題ファイル1つの追加だけではない。ほかのファイルを変えた・消した・2つ以上追加した。ファイル名の形が違う。ログには、機能追加なら小文字の issue- で始まるブランチ名にする、という一行も出る（今日の演習では、使わない）。下の「余計な変更を取り除く」を見る。
ファイル名は半角英小文字・数字・ハイフンと .json にしてくださいファイル名に、大文字・_・空白・日本語、または .JSON などが入っている。ファイル名を、小文字のニックネーム＋ .json に直す（git mv 古い名前 新しい名前）。
author をテンプレートから書き換えてください（question、explanation、choices も同じ）見本の値のまま。その項目を、自分の内容に書き換える。
choices に重複があります同じ選択肢が2つある。4つが全部違う文になるように直す。
choices は空でない文字列をちょうど4つ指定してください4つでない、または空の選択肢がある。4つにそろえる。
answer は 0 から 3 の整数にしてくださいanswer が 0〜3 の整数でない（4、"1"、1.5 など）。0〜3 の数字にする（引用符で囲まない）。
JSON の構文が正しくありません, や " の書き間違い。書き方の例と見比べて直す。Codex に「JSON の構文だけ直して」と頼んでもよい。

直し方（共通）: ブランチのファイルを直して、commit・push する。PR は作り直さなくてよい。push すると、同じ PR が更新され、検査がもう一度走る。

余計な変更を取り除く: Codex に、次のように頼む。

私のブランチの変更を、questions/<ニックネーム>.json を1つ追加しただけの状態にしてください。git merge-base origin/main HEAD で出る共通祖先の commit の状態に、それ以外のファイルを戻してください。私が余計に足したファイルは、消してください。そのあと commit して、ブランチ add-quiz-<ニックネーム> を push してください。main への push と force push はしないでください。実行する前に、コマンドを見せてください。

直ったかは、上の git diff --name-status origin/main...HEAD で確かめる（A questions/<ニックネーム>.json の1行だけになる）。ファイルを戻すとき、最新の origin/main の状態に戻すのではなく、共通祖先の状態に戻すのがこつである（最新の main に戻すと、ほかの人が main に入れた変更が、自分の変更として混ざることがある）。

マージボタンが押せない

  • Approve がまだ: 一番多い原因。組の相手の Approve が必要である（自分では付けられない）。相手に頼む。付かないときは、先生に声をかける。
  • 検査が終わっていない、または赤い: 緑になるまで待つ。赤なら上の手順で直す。
  • PR が競合している（conflicts）と出る: ほかの人と同じファイル名（ニックネーム）を使っている可能性がある。ニックネームが重ならなければ、競合は起きない。すぐに先生に声をかける。
  • 相手が Comment で直してほしい点を書いている: 直して push し、相手に見直しを頼む。
  • ボタンの近くに、足りない条件が書かれている。読んでも分からなければ、先生に見せる。

第4部 宿題: 自分のアプリをリポジトリにする

今日の流れは、そのまま自分のアプリに使える。先に決めておくこと: 秘密は、最初の commit にも入れない。一度 GitHub に上げた秘密は、あとから消しても、履歴に残る（その場合は、キーを無効にして作り直す）。

手順

  1. アプリのフォルダで、.gitignore を先に作る。入れるものの例: .env、*.key、node_modules/、.DS_Store、ビルドの出力フォルダ。使っている言語の定番の .gitignore を、Codex に作ってもらってもよい。
  2. 秘密を点検する。API キー・パスワード・トークンが、コードの中に書かれていないか。あれば、.env に移して、コードは環境変数から読む。.env や、キーを書いたファイルは、絶対に commit しない。
  3. リポジトリにする。 
    git init
git status

    git status の一覧に、.env など入れたくないものが出ていないことを確かめてから、次へ進む。

  4. 最初の commit。 
    git add .
git status
git commit -m "最初の commit"

    git add . のあと、もう一度 git status を見て、秘密のファイルが入っていないことを確かめる。

  5. GitHub にリポジトリを作って push する。最初は private（自分だけが見られる） にしておく。 
    gh repo create <アプリ名> --private --source . --remote origin --push
  6. 機能を足すときは、ブランチ → PR → マージを1回やる。今日と同じ流れで、git switch -c <機能の名前> → 編集 → commit → push → PR → マージ。1人で作るときも、PR を使うと、変更の単位が GitHub に残る。

Codex に頼むときの文例

このフォルダを Git のリポジトリにしたいです。まず .gitignore を作り、.env と、秘密や不要なファイルが入らないようにしてください。そのあと、API キーやパスワードがコードに直接書かれていないかを探して、場所だけ教えてください（書き換えは、私が確認してから）。commit と push は、私が頼むまで行わないでください。
